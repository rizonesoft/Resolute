### adversarial: needs-attention

Findings are based on the candidate’s code paths; destructive reproductions were not executed.

1. **P1: Restore can overwrite an existing database despite `--database <new-name>`.** `tools/refdata/refdata.py:349` executes the dump without restricting its database access. Reproduce by taking a normal `mysqldump --databases refdata` backup, making subsequent authoring changes, then running `refdata.py restore backup.sql --database recovery`. The dump’s `USE refdata` overrides the selected database, and its table replacement statements destroy the newer authoring data. Checking that `recovery` does not exist provides no protection. This is a standard dump format, not a tampered input. Restore needs an enforced destination boundary or must reject incompatible dumps before executing them. [MySQL documents these embedded database-selection statements](https://dev.mysql.com/doc/refman/8.4/en/mysqldump-sql-format.html).

2. **P1: Interrupted first startup can permanently leave passwordless root access.** `tools/refdata/server.ps1:208` treats an existing data directory as completed credential initialization, while password assignment occurs only at line 230. Reproduce on a fresh installation by interrupting startup after the passwordless option file is written at line 218 but before `ALTER USER`, then running `-Start` again. If the daemon survived, line 203 immediately reports success; after a reboot, `$fresh` is false and password assignment is skipped. The server can then hold real authoring data accessible through loopback without authentication. Initialization needs a recoverable credential-completion state, and startup must verify authentication before reporting success.

3. **P1: Workflow transitions do not hold their validation locks through the update.** `tools/refdata/refdata.py:223` invokes review, reopen and stamp without a transaction. Their procedures use `SELECT ... FOR UPDATE`, followed by unconditional status updates, but never start a transaction themselves. Reproduce with two authors concurrently running `stamp` and `reopen` against the same reviewed version: both can read `reviewed`, after which reopen clears approval and stamp nevertheless succeeds using its earlier status. The resulting version can be stamped without a current review, or reopened after stamping, depending on update order. The real path is the documented shared authoring server. Each transition must atomically cover validation, status mutation and changelog insertion. [MySQL requires an explicit transaction or disabled autocommit for these locking reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html).
