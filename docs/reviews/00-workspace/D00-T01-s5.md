## The three questions

**Does it make sense?** Yes. Five gates that must each be remembered are five gates that get skipped, and "did you run the checks" now has one answer.

**Is it logical?** After one round. The decisive correction is that a count of zero findings is not evidence of a clean tree when the thing producing the count could not run.

**Did it break anything else?** No. The final run is 10 gates ok and 1 not present, exit 0, with the launcher and extension both building and the tidy count unchanged for the code that was already covered.

## Findings

### F1 -- the gate reported success on analysis that never ran -- correctness -- FIXED in `cecf69f`

Raised by the independent review as a **P1**, and it is the worst finding in this file so far because of where it is.

The tidy loop ignored every `clang-tidy` exit code, and `Get-TidyCount` recognised only `warning:` lines. Analysis that cannot complete emits **errors and zero warnings**. A broken config, an unreadable compile database, or a failed analyser therefore produced a count of 0, which is under any baseline, and the gate printed `ok`.

**This is the fifth check this file has caught reporting success while doing nothing.** `§1` found a bootstrap printing "reskit/ is unchanged" while deleting a toolchain. `§2` found a script warning "No .exe found" immediately after linking one. `§4` found a build script that built no launcher, and a Debug binary deployed as Release. This one is the first I wrote myself, in the section whose entire purpose is that the checks cannot be skipped, while writing comments about that exact failure mode.

**The obvious half of the fix is not the half that works.** The review proposed tracking failures for every invocation. Driven with an invalid `.clang-tidy` key:

```
tidy  FAILED  analysis did not complete: 0 of 14 invocation(s) exited non-zero,
              56 error diagnostic(s). The finding count is not evidence until
              this is clean.
```

`clang-tidy` **exits 0** on an unknown config key. Exit codes alone would not have caught the reproduction the reviewer used to find it. The load-bearing check is the scan for `clang-diagnostic-error`, `error: ` and `Error while processing`. Both are kept, because a failed invocation and a completed-but-erroring one fail differently and either can hide a count.

### F2 -- an entire shipped extension was analysed by nothing -- integration -- FIXED in `cecf69f`

Raised as a P2. The gate read only the **root** compile database. `RegStudio` is commented out of the root `CMakeLists.txt` and builds standalone, so it appeared in **0 of 35** root entries, and its own build tree exported no database at all.

So the combined gate reported static analysis passing over a tree containing a shipped executable it had never looked at. `scripts/build.ps1` now exports a database for every extension and the gate reads all of them.

**The baseline moved 59 to 103 and the split is what makes it safe:**

| | findings |
| --- | ---: |
| launcher + shared | 59, **unchanged** |
| `RegStudio`, newly covered | 44 |
| total | **103** |

The 59 not moving is the check on the move. Had it shifted, the raise would have been hiding a regression inside a coverage change. `todo/.tidy-baseline` records the raise with that reasoning, because that file states the ratchet only goes down, and a raise has to earn its paragraph rather than just its number.

### F3 -- "both architectures", for the second time in one file -- consistency -- CORRECTED in the plan before building

`§1` recorded x86-64 as the only architecture built, with `i686` "noted and not wanted". `§4` corrected the inherited phrase two sections ago and this section still carried it. Corrected to both **configurations**, which is what "both" reaches for on a single-target toolchain.

Worth noting that `§5` also carried it in the file-level Verification block, and that `D09 T01 §1` keeps the phrase legitimately, because the AutoIt suite really does ship a 32-bit and a 64-bit binary.

### F4 -- a claim was filed into the wrong section, and this section falsified it -- record -- CORRECTED

An `absent scripts/check-all.ps1` claim sat in the body of `D00 T04 §5`, which is about the adjacency advisory and says nothing about this script. The sentence it supports is in `D00 T04 §1`. Both sections are stamped, and this section makes the claim false.

Moved to the sentence it supports and flipped to `exists`. No checklist item, tick or `Done when:` changed, and `§1`'s reasoning was correct: what it required of this section is exactly what this section did.

I filed that claim one section ago. Claims were added to `D00 T04 §5` as a batch and this one belonged to a different section entirely.

### F5 -- writing about a claim filed a claim -- record -- CORRECTED before committing

Found by the claim count going from 61 to 62 after an edit that added no claim.

The validation paragraph explaining F4 **quoted the claim's literal HTML-comment syntax**, and `todo-claims.py` parsed the quotation as a real claim: an `absent` assertion this very section was about to falsify. The grammar has no escape, so documenting a claim files one.

Written around by describing the claim instead of reproducing it. Worth knowing before somebody writes a guide to the claim syntax inside a TODO, which is a thing this tree would plausibly do.

### F6 -- a checkpoint written before the build had two configurations -- record -- CORRECTED

The report item asked for "three passes and one failure". A single deliberate warning now fails **two** gates, `build Debug` and `build Release`, because the same source is compiled twice. That is the gate being right. The item now states what one warning should do.

### F7 -- a stale preset name in another section -- consistency -- CORRECTED

Found while wiring the test gate. `D00 T02 §1` asked for `ctest --preset x64-debug`. `CMakePresets.json` declares `debug` and `release`, and has **no `testPresets` block at all**, so `ctest --preset` cannot work until that section adds one.

Corrected in place with a dated note rather than filed, because it is one factual line in an open section I was already editing to add a required reciprocal XREF, and leaving a known-false command in the tree is the reassurance-that-hides-a-defect pattern from `§2`.

## Two probes worth keeping

Both were changed after their first run taught something.

**The build-warning probe moved file.** Put in `src/main.cpp` it failed the build gates *and* the claims gate, because `main.cpp` carries a `lines` claim and appending changed the count. Two gates doing their jobs, and a worse demonstration of one. Moved to `theme.cpp`, which carries no line claim.

**The coverage-floor probe was rebuilt.** Forcing the floor by raising `COVERAGE_FLOOR` in the source tripped a different claim: `'COVERAGE_FLOOR = 3' in scripts/todo-claims.py matches 1 times`. The floor value is itself claimed, so lowering it to pass is not available, which is the check catching the person testing it. The fixture was rebuilt to remove claims from two covered blocks instead.

## Independent review

`codex review --commit e7d634f` (gpt-6-astra, high effort) returned **one P1 and one P2, and both were right**.

Its advantage was again probe construction, and this time it built an isolated fixture: a scratch directory with a deliberately invalid `.clang-tidy` and a source including a nonexistent header, run through the real `clang-tidy` binary. That is how it established the gate would report `ok` on analysis that could not complete, rather than arguing from reading the loop.

Five sections, five times the reviewer's value came from running something rather than reading it. The pattern is now specific enough to act on: **when I build a checking tool, the thing to test is not whether it catches a bad input but whether it catches its own absence.**
