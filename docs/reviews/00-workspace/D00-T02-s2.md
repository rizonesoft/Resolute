## The three questions

**Does it make sense?** Yes. The destructive half of the suite has somewhere safe to point, which is the thing the AutoIt tools never had and the stated reason their most dangerous paths went untested for years.

**Is it logical?** After one round, and the correction is the interesting part: the guard was applied to every path except the one whose destructor deletes a directory.

**Did it break anything else?** No. 19 tests pass unelevated, the tidy baseline is unchanged at 169 over 18 TUs, and `HKCU\Software\Rizonesoft` still holds exactly `ClassicPanel` and `Office` after every run.

## Findings

### F1 -- the boundary guard was not applied to the fixture's own root -- adversarial -- FIXED in `339bfd9` (independent) [major]

Raised by the independent review as a **P1**, and it is the section's central safety property failing in the one place a mistake is expensive.

Every **member** resolved its argument and compared it component-by-component against the root. The **constructor**, which decides where the fixture's root lives and whose destructor calls `remove_all` on it, used a separate hand-rolled check.

That check tested `is_absolute()`. On Windows a **root-relative** name such as `\escape` is *not* absolute, because `is_absolute()` requires a root name **and** a root directory. And `base / "\escape"` keeps the base's drive while **discarding its directories**, so the fixture's root became `R:\escape`, and its destructor deleted it. The reviewer reproduced both the escape and the deletion.

**Two checks for one boundary is what allowed this.** The careful one was written first, for the members, and the constructor got a quick one because it looked like a simpler case. There is now one function: constructor and members both call `ResolveUnder`, which refuses absolute, drive-qualified and root-relative names and refuses a path resolving to the root itself.

**The section had already moved the registry root for exactly this class of risk** and then left the filesystem root reachable. Recognising a danger in one place is not the same as looking for it in the other.

### F2 -- the sweep reported success while leaving residue -- correctness -- FIXED in `339bfd9` (independent) [major]

Raised as a P2. `SweepStoreRoot` called `remove_all` with an `std::error_code` and discarded it. A read-only leftover meant the sweep returned quietly with the residue in place, the next test ran against contaminated state, and the suite could still report success.

Both sweeps now check the status **and** verify the outcome, because `remove_all` does not always report a failure it did not perform, and both fail the run naming the path.

**This is the sixth time this repository has caught that exact shape in its own tooling**, after `§1`'s bootstrap, `§2`'s extension script, `§4`'s build script and Debug-as-Release deploy, and `§5`'s tidy gate. The lesson is no longer that the shape exists; it is that I keep writing it in the cleanup path specifically, where nothing is looking.

### F3 -- a fixture that could not read back what it wrote -- correctness -- FIXED in `339bfd9` (independent) [major]

Raised as a P2. `GetString` used a fixed 1,024-character buffer, so `SetString` accepted a valid registry string that `GetString` could not read back, throwing `ERROR_MORE_DATA`.

That is worse than a size limit: `tests/README.md` makes reading the effect back the one non-negotiable convention, and a fixture that cannot do it for a legitimate value quietly disables the rule for anyone who hits the limit. It now asks the registry for the size first, proven with a 4,096-character round trip.

### F4 -- RAII does not survive a process death, and the checkpoint could not see it -- adversarial -- FIXED before committing (self) [major]

Found by probing rather than by the checkpoint.

The item asks that a test throwing mid-run leave no residue, and RAII delivers that. So does the checkpoint's assertion. But a process that **dies** runs no destructors, and a probe that seeded both fixtures then called `std::abort()` left `abort-residue` behind in the registry and the tree:

```
process exit=-1073740791     destructors do NOT run
registry leftover: abort-residue
tree leftover    : abort-residue, seeded.txt
```

Every in-test assertion passed throughout. The checkpoint as written could never have caught this, because it only observes a run that completed.

Closed by sweeping both roots at run **start** as well as end, so a previous crash's residue cannot outlive the next run. Driven against the residue the abort actually left.

**What it still does not cover, recorded rather than left to be discovered:** two concurrent test processes would sweep each other's roots. One process today and `ctest` is not configured for parallelism, so it is a limitation rather than a bug, and it is written down where somebody adding `-j` will meet it.

### F5 -- the registry root sat one level below live user settings -- adversarial -- CORRECTED before implementing (self) [minor]

The section specified `HKCU\Software\Rizonesoft\Fixtures`. On this machine that key's parent holds real product settings: `ClassicPanel` and `Office`, both checked directly.

Teardown is recursive deletion. A deletable fixture root one level below live user data is one arithmetic mistake away from taking it, and `AGENTS.md` requires a destructive path be confirmed rather than trusted. Moved to `HKCU\Software\ResoluteTestFixtures`, which shares no parent with product data except `HKCU\Software` itself and cannot be mistaken for somebody's preferences.

### F6 -- the unelevated claim was checked rather than assumed -- record -- CLEARED (self) [minor]

Not a defect. Recorded because the item's third requirement would have been expensive to discover late.

Setting a DACL on a file this process owns succeeds where `IsInRole(Administrator)` is **False**, verified before any fixture code was written. The section now also states what genuinely *does* need elevation and is therefore **not** covered here: taking ownership of an object owned by somebody else needs `SeTakeOwnershipPrivilege`, which `D04 T01 §1` will meet and which these fixtures do not solve.

## What the guard is actually doing

Worth stating because it is easy to build the weaker version:

```
refused    \Software\Rizonesoft     absolute
refused    ..\..\Rizonesoft          traversal
refused    HKLM:\Software            hive qualifier
refused    ..\escaped.txt            resolves outside the root
refused    C:\Windows\escaped.txt    drive-qualified
refused    \escaped-root             ROOT-RELATIVE, the one that escaped
ALLOWED    a\b\..\c                  stays inside, lands at <root>/a/c
```

The last line is the point. A guard that pattern-matched on `..` would refuse a legitimate path and still miss anything escaping without the characters it looks for. Resolving first and comparing against the root makes it a boundary check rather than a spelling check, and a test asserts the allowed case so nobody "hardens" it into the wrong thing.
