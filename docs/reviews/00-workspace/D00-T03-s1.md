## The three questions

**Does it make sense?** Yes. The section asked for the ExoSuite and RegStudio histories to survive the intake, and they did: `git log -- shared/` reaches `efdce61` and `09b1f92`, and `c9b8a0b` is an ancestor of `HEAD`. Scope stayed inside the merge; the one adjacent thing found was filed rather than fixed.

**Is it logical?** Yes, with corrections made during this review. The retirement of Console and `libvterm` is internally consistent: Console was `libvterm`'s only consumer, `CMakeLists.txt:47` records why at the line where `add_subdirectory` stood, and the source stays reachable at `ac97ed7:extensions/Console`, 1,762 lines.

**Did it break anything else?** No build consumer references Console or `deps/`; the only surviving mention is the explanatory comment. `git ls-files samples` is empty and no embedded-repository warning appears.

## Findings

### F1 -- four claims pointed into gitignored `samples/` -- consistency -- FIXED (self)

Four `claim` comments in this file addressed `samples/ExoSuite/...`. They held only because the operator's local checkout happens to exist on disk. `/samples/` is gitignored by this section's own design, so on any fresh clone `todo-claims.py` would have reported four stale claims and the checker would have been wrong about a tree that was fine. A self-checking plan whose checks break for everyone but one machine is worse than no check, because it teaches the next reader to ignore the output.

Fixed by repointing all four at the repository's own copies, which are byte-identical: `exokit/Bootstrap-ExoKit.ps1` matches the samples copy at md5 `b8a489ae9e0c` and both contain `llvm-mingw` 4 times; `src/main.cpp` is 573 lines in both.

### F2 -- the Test checkpoint named components, not paths -- record -- FIXED (self)

The checkpoint required ten `shared/exo-ui` files to be present and named them as `animation`, `contentview`, `listview`, `popupmenu`, `typography`, "headers and sources". Re-running it in this review produced **three false MISSING results**, because `contentview`, `listview`, and `popupmenu` live under `controls/` while the other two do not. All ten are present and always were.

The defect is not the wrong guess, it is that the checkpoint could not be executed the same way twice. This is the unfalsifiable-checkpoint failure mode wearing its other face: a check too vague to fail correctly is also too vague to pass correctly, and the next reader gets a false alarm on a healthy tree. The ten exact paths are now written into the checkpoint, along with the note that Console is checked at `ac97ed7` rather than `HEAD` because `e1f26a1` deliberately retired it.

### F3 -- `AGENTS.md` did not describe the root it now has -- consistency -- FIXED (self)

The section's own item says "Done when: the layout below is true and `AGENTS.md` agrees with it." The layout table in `AGENTS.md` listed `src/`, `shared/`, `extensions/`, and `resolute_au3/` but not `exokit/` or `resources/`, both of which the merge landed and both of which are tracked. Added, with `exokit/` noting that `D00 T03 §3` renames it to `reskit/`, so the entry does not go stale silently when that section runs.

### F4 -- the build depended on the gitignored `samples/` tree -- integration -- ROOT CAUSE CLEARED, residue FILED to `D00 T01 §2` (self)

At the start of this review, `build/release/CMakeCache.txt` resolved its whole toolchain into the samples checkout:

```
CMAKE_CXX_COMPILER:STRING=R:/.../Resolute/samples/ExoSuite/exokit/llvm-mingw/bin/clang++.exe
CMAKE_MAKE_PROGRAM:FILEPATH=R:/.../Resolute/samples/ExoSuite/exokit/ninja/ninja.exe
CMAKE_COMMAND:INTERNAL=R:/.../Resolute/samples/ExoSuite/exokit/cmake/bin/cmake.exe
```

The merged tree's own `exokit/` held five PowerShell scripts and no toolchain. `Init-ExoKit.ps1:20` sets `$ExoKitRoot = $PSScriptRoot`, so a real bootstrap populates `Resolute\exokit\`, which was empty at review time.

This matters beyond tidiness. The section states the local checkouts "may stay on disk; they are working copies, not repository content", and that is not true while the build resolves its compiler through one of them. Deleting `samples/`, which the section says is safe, breaks the build. The "52/52 targets" evidence recorded in `ffa97c3` is real and the sources it compiled were the merged tree's, but it is **not** evidence that the merged tree bootstraps and builds on its own, which is what the checkpoint's full-bootstrap clause asks for.

**Cleared during this review.** Rather than record the gap and move on, the review ran the real thing: `exokit/Bootstrap-ExoKit.ps1` downloaded and installed the toolchain into the repository's own `exokit/`, exit 0.

```
cmake version 4.2.3
ninja 1.13.1
clang version 21.1.8   (llvm-mingw 20251216)
```

Those are the three versions the section's Current state block records, so the bootstrap the file describes is the bootstrap that ran. `build/release` was then deleted and reconfigured from scratch:

```
CMAKE_CXX_COMPILER:STRING=R:/conclave/projects/Resolute/exokit/llvm-mingw/bin/clang++.exe
CMAKE_MAKE_PROGRAM:FILEPATH=R:/conclave/projects/Resolute/exokit/ninja/ninja.exe
CMAKE_COMMAND:INTERNAL=R:/conclave/projects/Resolute/exokit/cmake/bin/cmake.exe
```

`grep -c samples build/release/CMakeCache.txt` returns **0**. The build then produced 52/52 targets, and the shipped set reproduced the recorded figures byte for byte: `ExoSuite.exe` at 1,380,352 bytes plus `System/ExoUI.dll` and `System/Lucide.dll`, 3.9 MB total. `git status` showed only this review's own edits, so 850 MB of toolchain and a full build left nothing untracked: the `.gitignore` rules cover the directories, not merely the build output.

The section's claim that `samples/` is disposable is now true, and the checkpoint's full-bootstrap clause is satisfied by an actual bootstrap rather than by a build that happened to reuse a neighbouring toolchain.

What remains filed to `D00 T01 §2`, which owns the toolchain: making the presets resolve the bootstrapped toolchain **in preference to whatever is on `PATH`**, and proving it with `samples/` moved aside rather than merely absent from a cache. Clearing a stale cache once is not the same as a preset that cannot drift again, and that durable guarantee is that section's to give.

### F5 -- `test_font.cpp` tracked at the repository root -- consistency -- FILED to `D00 T02 §1` (self)

The intake gitignored `test_font.exe` and `test_font.obj` as build output but let the source travel. It sits at the root, is built by no target, and appears in no layout. `D00 T02` already calls it a scratch file without owning its removal, so an item now says so there, with a claim guarding it.

## Independent review

`codex review --commit ffa97c3` (gpt-6-astra, high effort) returned two P2 findings. Both were checked against source, both were right, both fixed in `8ba1f20`:

1. The static-linking diagnosis blamed the `SHARED` targets. `src/CMakeLists.txt:10` links `ExoUI_static`, so ExoUI was already static. The real dependency is `LucideIcons::Load()` at `shared/exo-ui/src/icons.cpp:15` calling `LoadLibraryW` for `Lucide.dll`. The proposed verification was unfalsifiable in the dangerous direction: an import-table check cannot see a runtime `LoadLibrary`, so it would have passed a tool that still shipped a DLL.
2. "No external dependencies at all" was false. `shared/lucide/CMakeLists.txt:9` fetches `sammycage/lunasvg` v3.5.0 through `FetchContent`. Retiring the submodule bought the `--recursive` flag, not dependency freedom.

**Second pass, on the fix commit.** The first review read `ffa97c3`, so it could not have seen `8ba1f20`, the commit that acted on its own findings. Reviewing only the ship commit leaves the fix unexamined, which is the gap this project's own rule about independent review exists to close. `codex review --commit 8ba1f20` returned no actionable regressions and independently re-measured the four claims that commit added:

```
shared/lucide/CMakeLists.txt: lunasvg = 6 (expected 6)
shared/exo-ui/src/icons.cpp: LoadLibraryW = 2 (expected 2)
src/CMakeLists.txt: ExoUI_static = 1 (expected 1)
.gitmodules tracked: False
```

The stamp commit `0dbfa56` is deliberately not reviewed: it carries the stamp and nothing else, and reviewing a record of a review is circular.

A process defect surfaced alongside them: the skill's documented invocation passed a prompt to `codex review --commit`, which the CLI refuses with `the argument '--commit <SHA>' cannot be used with '[PROMPT]'`. The stdin form `-` fails identically, verified. That prompt could never have run, so the skill was corrected to the bare form.
