## The three questions

**Does it make sense?** Yes. The toolchain already worked; what it lacked was every property that makes it trustworthy on a machine other than the one it was written on. All of them are now driven rather than asserted.

**Is it logical?** After two rounds. The decisive change is that `bootstrap.ps1` and `cpp-env.ps1` now share one rule for what counts as the pinned version, so they cannot disagree about what is installed.

**Did it break anything else?** The release build still produces 52/52 and the executable carries the manifest, read back from the binary. `Init-ResKit.ps1` still resolves after llvm-mingw was reinstalled through the new path. `git status` stays clean through a full bootstrap.

## Findings

### F1 -- the abort message was a lie for one window -- correctness -- FIXED in `8437dd5` (independent) [major]

Raised by the independent review, which reproduced it. Under `-Replace` the old install was deleted **before** the download, so a network failure or a hash mismatch destroyed a working toolchain while the abort printed "reskit/ is unchanged".

The message being wrong is worse than the deletion being wrong. A destructive failure that announces itself can be recovered from; one that reports safety cannot, because nobody goes looking. The order is now download, verify, extract, then replace, which is the atomic-write requirement `AGENTS.md` states.

Proven: corrupting a hash during `-Replace` leaves `ninja.exe` present before and after.

### F2 -- a stale stamp let a foreign binary pass -- correctness -- FIXED in `8437dd5` (independent) [critical]

Also raised by the review, with a sharper probe than mine. My own test hid the whole `reskit/ninja` directory, which took the stamp with it, so the fallback correctly rejected the PATH copy. **The reviewer removed only the executable and left the stamp**, at which point resolution fell back to PATH while the check still read the repository's stamp: an unrelated binary accepted on an attestation belonging to something else.

Fixed by making the capability explicit rather than inferred. `toolchain.json` now carries `reportsOwnVersion`: true for CMake and Ninja, whose own answer is authoritative and which no stamp may override; false for llvm-mingw, which reports a clang version and never its own release. The stamp is read only for the repository copy and only for a component that cannot report its release, and a failed probe is never the pin.

Proven with the reviewer's own case: removing `reskit/ninja/ninja.exe` while leaving its stamp now finds this machine's ninja 1.13.2 on PATH and rejects it by name.

### F3 -- manifest-controlled recursive deletion was unbounded -- adversarial -- FIXED in `9874bf8`, before the review ran (self) [critical]

Found by self-review. Every `Remove-Item -Recurse -Force` deleted a path built by joining `reskit/` to a `dir` value read from `toolchain.json`, with no bounds check. That file is tracked and trusted, but a recursive delete driven by a config value is exactly what `AGENTS.md` means by an unconfirmed destructive path: `"dir": "../.."` would have deleted the repository.

The independent review raised the same defect against `6bb635e`, which predates the fix, so it was correct for what it read. It separately reviewed `9874bf8` and confirmed the guard accepts every configured directory while rejecting parent traversal, sibling-prefix paths, and `reskit` itself.

### F4 -- a parser stack trace is not failing by name -- consistency -- FIXED in `87fbb48` (self) [minor]

Found by self-review. Both scripts exited 1 on a malformed `toolchain.json`, which is right, and printed a raw `ConvertFrom-Json` trace, which names the parser rather than the problem. This section's own item promises the locator fails by name.

### F5 -- an optional field silently changed what was trusted -- adversarial -- FIXED (self) [critical]

Found in this review, and it is F2's fix examined for the same shape. `reportsOwnVersion` is read from JSON; a component omitting it yields `$null`, which is falsy, which routes that component down the **stamp-trust** path. An absent field would therefore have quietly relaxed the check that had just been tightened.

Every field both scripts rely on is now required, and a component missing one fails by name:

```
cpp-env: toolchain.json component is missing a required field
  component: cmake
  missing  : reportsOwnVersion
```

### F6 -- the self-contained claim is narrower than the section originally stated -- record -- corrected in the plan before implementing (self) [minor]

Recorded because the gap is the interesting part. The item asked for proof on "a machine with no Visual Studio and no Windows SDK". This machine has both, verified directly, so that proof was unavailable here.

What was proven instead: a program calling `CreateFileW` and `D2D1CreateFactory` compiles, links, and **runs**, and the compiler's own dumped search paths contain nothing outside `reskit/` — three include paths and four library paths, all inside it. That is the self-contained claim as far as it can be established here.

It is **not** the same as proving a machine without Visual Studio works, because absence cannot be simulated on a machine that has the thing: a toolchain can fall back to a registry key or a well-known path. `§7` owns that, with a new `Needs` value and a checkpoint that additionally requires the binary to **run** there, since a successful link says nothing about what the loader will ask for.

## What the floor check actually buys, stated honestly

The mechanism is mingw-w64's own header guards on `NTDDI_VERSION`, 161 files of them. No `clang-tidy` rule was needed. Proven both ways with the macros `CMakeLists.txt` sets:

```
GetCurrentPackageInfo2, gated at NTDDI_WIN10_19H1
  at 0x0A000006 (1809)  exit 1, "use of undeclared identifier 'PackagePathType_Effective'"
  at 0x0A000007 (19H1)  exit 0
```

The second line is the falsifiability check; without it the failure could have been a typo.

**The guarding is incomplete and the section says so.** `GetMachineTypeAttributes` is a Windows 11 API gated only at `_WIN32_WINNT_WIN10`, a single value covering every Windows 10 and 11 release, so it compiles cleanly at the 1809 floor. This catches an above-floor API when the header gates on `NTDDI_VERSION` and silently permits one gated only at `_WIN32_WINNT`. A real check with a known hole is worth having; calling it a guarantee would not be.

## Independent review

`codex review --commit 6bb635e` (gpt-6-astra, high effort) returned **three P2 findings**. Two were new and both were right; the third was already fixed in a later commit it had not read.

Its value here was specificity of probe. On F2 it constructed a case mine had missed by one step: I removed a directory, it removed only the executable and left the attestation behind. That is the difference between testing that a check fires and testing what the check actually trusts.

One process note: the first two invocations against this commit produced no output within their window, one at 570s and one that ran much longer. A third succeeded. A smaller commit reviewed in seconds, so the cause appears to be commit size rather than availability.
