## Findings

### F1 -- the chain was wrong, in the way that matters most -- correctness -- FIXED in `b541b9a` (independent) [major]

`_section_edges` walked only the `Depends On` column and ignored the frontmatter `depends_on`, of which **fifteen are declared**. The chain read 17 sections deep against an actual **30**, and ended at `D05 T02 §5` rather than `D05 T07 §4`.

This is the worst possible defect for this particular feature. The report's only purpose is naming the path where delay costs most, and it was naming a different path. It would have been read as evidence and acted on through `groom-plan`.

Worth recording that the reviewer predicted both the corrected depth and the changed endpoint before the fix, and both matched exactly.

### F2 -- a documented reference form matched nothing -- correctness -- FIXED in `b541b9a` (independent) [major]

A dependency written `TNN §N`, which `AGENTS.md` documents alongside `§N` and `DNN TNN §N`, matched no node and truncated the chain silently at that point. I had pattern-matched the two forms I had seen in the tree rather than using `resolve_ref`, which already handled all three.

Proven: rewriting `D00 T01 §1`'s dependency as `T03 §3` leaves the chain at 30. Before the fix it would have cut the intake prerequisites off entirely.

### F3 -- unreadable evidence was reported as absent evidence -- correctness -- FIXED in `b541b9a` (independent) [major]

`_filing_couplings` discarded the ledger's list of headings it could not parse and swallowed every exception, so a broken findings file produced an empty list and the report then stated that no review had filed a finding. "No evidence" and "the evidence could not be read" are opposite claims, and it made them identical.

Proven: breaking one category drops the count from 4 to 3 **and** prints the file, line, and reason, describing the list as a floor rather than the picture.

**This is the third occurrence in this TODO file of one shape**: the claims checker dropping a split claim, the coverage floor passing with no claims, and now this. The answer this file records for the `correctness` category is that a new check ships with a self-test constructing its **failing** case, and I did not apply it here. The self-test now guards the return shape, because a caller unpacking two values cannot silently revert to ignoring the second.

### F4 -- the headline number counted work that cannot be delayed -- record -- FIXED (self) [minor]

Found in this review. The report led with "30 sections deep", of which three are already stamped. A shipped section cannot be delayed, so the number a reader acts on is the open depth, not the total.

It now reads `30 section(s) deep, 27 still open`, and says the shipped ones are shown for shape because they set the structure. Small, but the item's wording is "the sections on it are identified as the ones whose delay costs most", and three of them were not.

## What the tool deliberately will not do

The four couplings it reports all point **backwards**: the first section of the plan filed work to sections that come later. A tool acting on that signal would move the intake after the toolchain it fed, which is exactly wrong, because there was no C++ tree to build a toolchain around until the intake landed.

The filings are work **discovered** early, not work **needed** first, and nothing in the data separates those two. That is why item 3 requires the tool to propose only, and it is enforced structurally rather than by intent: the `sequence` branch contains no `open(`, no `.write(`, no `write_text`, no `mkdir`, no `rename`, shown by search over the branch.
