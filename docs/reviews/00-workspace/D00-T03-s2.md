## The three questions

**Does it make sense?** Yes. The section asked for the product name to become Resolute and for the executable to carry the Rizonesoft identity. The build produces `Resolute.exe` and no `ExoSuite.exe` in either configuration, and the identity reads back from the binary rather than from the source that produced it.

**Is it logical?** Yes, after one fix. The identity values were taken from `resolute_au3`, which `AGENTS.md` makes the source of truth, rather than invented. The copyright year is generated at configure time, which mirrors what the AutoIt launcher does at runtime with `@YEAR`.

**Did it break anything else?** The debug preset had never been built during this section and was built in this review: 52/52, `Bin/Debug/Resolute.exe`, identity intact. No consumer references the old target name.

## Findings

### F1 -- `IDI_APPFALLBACK` defined twice -- consistency -- FIXED

`src/main.cpp:264` carried a function-local `#define IDI_APPFALLBACK 102`, and this section added the same constant to `src/resource.h`, which `main.cpp` includes at line 5 and which the `.rc` now includes too.

It compiled, because an identical object-like macro redefinition is benign. That is what makes it worth fixing rather than tolerating: it is invisible until someone changes the resource id in `resource.h` and the local define silently keeps the old value, at which point the launcher loads the wrong resource as its fallback icon and nothing reports an error.

The duplicate was not wrong before this section. `resource.h` previously defined only `IDI_EXOSUITE`, and `IDI_APPFALLBACK` lived in the `.rc` alone, so the local define was the only way the C++ side could see it. Moving both identifiers into `resource.h` is what made it redundant, so the fix belongs in this section rather than filed.

This is the suite's central defect class in miniature: one value, typed in two places, which is the same failure that put fourteen copies of ReBar in the AutoIt tree.

### F2 -- the `Resolute_32.png` and `Resolute_48.png` assets are referenced by nothing -- consistency -- advisory

Confirmed by search across `src/`, `shared/`, `extensions/`, `resources/`, `exokit/`, and the CMake files: only `Resolute.ico` and `application.ico` are named, both from the generated `.rc`.

Not a finding against this section, which inherited them unreferenced and renamed them in place. Recorded so a later reader does not assume they are wired to something. They are plausibly wanted for a future About dialog or installer, which `D01 T01 §7` and `D06 T01` own.
