## The three questions

**Does it make sense?** Yes, after the section was cut down to what could honestly be built. It was written to produce the first cross-implementation pair and could not: the pair was circular, undrivable and destructive, and the instrument is the part that was real.

**Is it logical?** Only after round two. The instrument had four independent routes to reporting parity it had not earned, and the round-one version of this file would have stamped all four.

**Did it break anything else?** No. 36 tests pass where 31 did, the tidy baseline is unchanged at 169 over 21 translation units where it was 19, and every gate is green.

## Findings

### F1 -- `Ownership` does not do what the plan said it did -- record -- CORRECTED in `18a9c6a`

Found by validation, before any code, and it reaches past this section.

The plan had `Ownership` taking ownership of files, and `D04 T01 §1` described "the filesystem ACLs, read back by the verify step" with a reverse that "restores every path's owner and ACL". **`Ownership.exe` never calls `takeown` or `icacls`.** Its entire system effect is writing four registry trees:

```
HKCR\*\shell\runas          HKCR\Directory\shell\runas
HKCR\dllfile\shell\runas    HKCR\Drive\shell\runas
  \command = cmd.exe /c takeown /f "%1" /r /d y && icacls "%1" /grant administrators:F /t
```

It is a **context-menu installer**. The `takeown` runs later, in a process this tool never starts, when a user right-clicks something.

**The measurement already said so.** `D04 T01 §2` records `Ownership` at **2 net functions and 77 net lines**, which is a registry writer and not an ACL engine, and that figure was recorded without anybody asking what it implied. A number can be correct, committed, and still tell nobody anything, because reading it as a size is easier than reading it as a shape.

`D04 T01 §1`'s Job, its reverse item and its Freeze check are corrected to registry semantics in the same commit.

### F2 -- the section asked for something circular, undrivable and destructive -- record -- CORRECTED by narrowing the section before implementing

Three blockers, each sufficient on its own:

- **Circular.** Items said "the first ported tool" and "both implementations". No C++ `Ownership` exists, and `D04 T01 §1` lists **`D00 T02 §4`** among its own unmet dependencies. Each waited on the other.
- **Not drivable.** No `$CmdLine` handling exists in `Ownership.au3` or `ReBar.au3`, so every tool in the AutoIt suite is GUI-only. Driving one today needs coordinate clicking, which this section's own item 3 names as the cheaper substitute that **fails** the checkpoint.
- **Destructive to the developer's machine.** Those writes go to `HKCR`, need elevation, and add a "Take Ownership" entry to Explorer's context menu. Running one for a test is not a confirmation.

So the section builds the instrument and defers the first pair to `D04 T01 §1`, at **item granularity** so closure is detectable, with the reciprocal note written into that section rather than left implied.

**The line held here:** the checkpoint was corrected, not weakened to fit. It is falsifiable on its own, driven below.

### F3 -- unpadded hex collided two different binary values -- correctness -- FIXED in `7a70eb7`

Raised as a **P2** by the independent review, reproduced with a compiled probe.

Bytes were written with `std::hex` and no width, so `{0x01, 0x23}` and `{0x12, 0x03}` both encoded as `123`. Changing a `REG_BINARY` value between those two recorded **zero changes**. Two digits per byte, always.

### F4 -- an unreadable scope became an empty snapshot -- adversarial -- FIXED in `7a70eb7`

Raised as a **P2**, and the worst of the four.

`RegOpenKeyExW` failing was treated exactly like the key not existing: skip, return, report a valid-looking snapshot. Two runs that were both refused the same key produced two empty snapshots, compared equal, and the report said **PARITY** for a scope neither side had seen.

Every way the walk can fail to see the system is now an observation failure, carried on the snapshot, through `Record::Between`, into the serialised form, and into `Compare`, which can never return empty for one. **Absence remains an observation**: `ERROR_FILE_NOT_FOUND` means the key was seen not to be there, and that record is complete.

This is the same defect as `D00 T01 §5`'s tidy gate reporting `ok` on analysis that never ran, and `§1`'s and `§4`'s scripts before it. **Fourth time in this domain, in a different disguise each time.** The disguise here was the best yet, because an empty snapshot is the correct answer to a different question.

### F5 -- an empty registry key left no trace -- correctness -- FIXED in `7a70eb7`

Raised as a **P2**, reproduced with a probe: adding an empty child key yielded zero changes.

Only values were recorded, so creating or deleting a key with no values was invisible. An undo that removed values and left the key trees behind compared equal to a complete removal, which is **precisely** what `D04 T01 §1` compares key by key across `Ownership`'s four `HKCR` trees. The finding landed on the one comparison this section had just corrected that section to make.

Each key is now its own entry, `(key)` of type `key`.

### F6 -- a malformed row was discarded rather than refused -- adversarial -- FIXED in `7a70eb7`

Raised as a **P2**. A row short of six fields was skipped, so a record compared **equal** to one that did not contain the change the row described. An unknown operation character was worse: it fell through the `else` to `Changed` and was counted as a real observation.

Parsing is strict and throws `ParityError` naming the line and what was wrong.

### F7 -- the parser lost a trailing empty field, and a backslash -- correctness -- FIXED in `18a9c6a`

Found by writing the hand-written-record test, which is the only item in this section that produced a defect before the reviewer arrived.

`std::getline` **drops a trailing empty field**, so a row ending in an empty value parsed as five fields and was discarded. `Ownership` writes `HasLUAShield` and `NoWorkingDirectory` as **empty strings**, so this would have dropped two of the values the tool actually sets.

And `Unescape` swallowed the backslash of any escape it did not recognise, turning a hand-written `C:\fixture\a.txt` into `C:fixturea.txt`, which names a different file than the run touched. An assertion now covers it.

### F8 -- XREF reciprocity is enforced per FILE, not per section -- record -- filed, not fixed here

Found by probing rather than assuming: a deliberately bogus `-> XREF: D09 T01 §9` was inserted to check the parser sees indented XREF lines. It does, and the FATAL it produced names a **file**:

```
FATAL ... XREF to todo/09-au3-maintenance/TODO-01-au3-maintenance.md is one-sided
          -- todo/09-au3-maintenance/TODO-01-au3-maintenance.md does not point back
```

So a section-level XREF is satisfied by *any* back-reference anywhere in the target file. `D00 T02 §4` to `D04 T01 §1` was already green before the reciprocal note was written, on the strength of an unrelated file-header XREF. The note was written anyway, because the check passing is not the same as the reader being told.

Same shape as `§3`'s F6, where `plan --check` enforced ref, status and item count but not the Deliverable text. **The graph checks structure; nothing checks whether the structure means what it says.** Recorded here rather than fixed: it belongs to the tooling domain.

## What the instrument actually buys

Precision matters here, because "a parity driver" could describe something much weaker.

```
parity: cpp vs autoit
  1 differing field(s):
    registry|HKCR\Directory\shell\runas\command|(default)
      cpp: + REG_SZ cmd.exe /c takeown
      autoit: + REG_SZ cmd.exe /c DIFFERENT
```

**The record is taken from outside the run.** That is not a convenience. The AutoIt binaries cannot be instrumented, parse no command line, and expose four unnamed panes to UI Automation, so anything requiring the tool to report on itself could never compare the two implementations at all.

**A diff is a list of fields, never a boolean.** Comparing exit codes is how two tools that did completely different things both report success.

**And after round two, failing to observe is not observing no difference**, which is the property that makes the first two worth anything.

## Independent review

`codex review --commit 18a9c6a` (gpt-6-astra, high effort) returned **four P2, all four right**, every one reproduced with a compiled probe before it was reported.

Ten sections, ten times it found something by constructing a state I had not. What is different here is the **uniformity**: all four findings are the same defect wearing four costumes, and I had written the header comment saying "a diff is a list of fields, never a boolean" while shipping four ways for that list to be empty without justification.

The standing lesson sharpens again. `§6`: my probes test the states I designed for. `D00 T02 §1`: a defect the reviewer already found once is the cheapest probe available. `§3`: a hazard I have written a paragraph about is not a hazard I have fixed. This one: **I checked that the instrument reports differences correctly and never checked that it was capable of seeing them.** Every test I wrote handed it a scope it could read.
