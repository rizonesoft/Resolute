## The three questions

**Does it make sense?** Yes, and the section's own premise checked out. All 13 `.sni` descriptors in the AutoIt tree carry paths rooted at `R:\Workspace\Resolute`, 91 occurrences, and that directory does not exist. The failure this section prevents is documented in the repository rather than argued for.

**Is it logical?** After one round. The decisive correction is that separating build *trees* by configuration does nothing if the thing being built writes to one path for every configuration.

**Did it break anything else?** It removed three scripts that five tracked files referenced, and those five were updated. The references inside `§2`'s stamp and this section's own validation prose describe what was true at the time and were left alone.

## Findings

### F1 -- a Debug binary shipped as Release, and it had already happened here -- correctness -- FIXED in `67554f2` (independent) [major]

Raised by the independent review as a **P1**, the second of this project.

`RegStudio` wrote its executable to one path for every configuration. Build Release, build Debug, build Release again: nothing changed, so ninja reports the Release build up to date, the Debug executable is still at that path, and `build.ps1` deploys it as Release.

**The reviewer reproduced it and found the two files byte-identical. Re-checking this repository found it had already happened**: `Bin/Release/System/RegStudio.exe` was the Debug binary, 1,036,288 bytes rather than 772,096.

**The instructive part is that this section had already fixed a defect in that exact line and made things worse.** Validation found `CMAKE_RUNTIME_OUTPUT_DIRECTORY` set from `CMAKE_SOURCE_DIR`, which resolves to the repository root when the extension is built from the root rather than standalone. That was real, and correcting it to `CMAKE_CURRENT_SOURCE_DIR` fixed it while leaving a worse defect untouched, because the new value is still one directory shared by every configuration. Finding a bug on a line is not the same as understanding the line.

The output now derives from `CMAKE_CURRENT_BINARY_DIR`, which is already per configuration, and the script searches only that configuration's own build tree rather than taking the newest executable from a shared directory. Looking in a shared directory and sorting by timestamp is a guess; looking in exactly one place is an answer.

### F2 -- the launcher could only be built from the repository root -- correctness -- FIXED in `67554f2` (independent) [major]

Raised by the independent review as a P2. `cmake --preset` reads `CMakePresets.json` from the **current** directory, and the script never changed to the repository root, so `pwsh ./build.ps1 Resolute` from `scripts/` failed. The script it replaced set its working directory explicitly and this one dropped that without noticing.

Found by running the script from somewhere other than where I had always run it.

### F3 -- a failed compile discarded the compiler's diagnostics -- consistency -- FIXED in `67554f2` (independent) [major]

Raised by the independent review as a P2. Every command was piped to `Out-Null`, so a failed build printed `build: compile failed for Resolute` and nothing else. Ninja prints the failing command and the diagnostics on stdout, and all of it was thrown away.

This inverted `AGENTS.md`'s output discipline rather than applying it. Bounding output means keeping the log and showing a useful part of it, not discarding the log. The full output now goes to `build/logs/`, which is gitignored, and the last 25 lines print on failure. Driven with a deliberate syntax error, which surfaced the `FAILED` line, the exact clang invocation, and all three diagnostics.

### F4 -- "both architectures" contradicted a decision `§1` had already recorded -- consistency -- CORRECTED in the plan before building (self) [minor]

Found in validation. The item required building "for both architectures". `§1` had already settled it as a dated default: x86-64 is the only architecture built, ARM64 is out of scope until there is a machine to drive a test on, and `armv7` and `i686` are "noted and not wanted".

The phrase is inherited from the AutoIt suite, where all 13 descriptors set `CompileBoth=Y` and shipped an `X64` binary beside a 32-bit one. True of AutoIt, not true here. A section that builds what a stale phrase asks for would have added an architecture nobody decided to ship.

### F5 -- the output item named the wrong directory -- record -- CORRECTED in the plan before building (self) [minor]

The item asked that executables land "under `build/`". `build/` holds CMake's own trees; the shipped output is `Bin/<Config>/`, set at `CMakeLists.txt:40-41` and recorded in `§2`'s stamp.

Worth separating the requirement from its prescription: predictable, repository-relative, documented, one place, no absolute paths. `Bin/` satisfies all of it. Following the literal text would have moved the output, contradicted a stamped section, and mixed derived CMake state with shipped binaries, which is a worse outcome reached by being more obedient.

### F6 -- a build script that had never built the launcher -- correctness -- CORRECTED by deletion (self) [major]

`reskit/Build-All.ps1` decided whether to build the launcher with `Test-Path shell/CMakeLists.txt`. There is no `shell/` directory in this repository and there never has been, so `$HasShell` was false on every run and the script built extensions only, reporting success.

**That is the third script in this file to report success while doing nothing**, after `§1`'s "reskit/ is unchanged" on a destructive abort and `§2`'s "No .exe found" printed immediately after linking one. Deleted rather than repaired, because the section's deliverable is one command.

### F7 -- an escape sequence corrupted the record -- record -- CORRECTED (self) [minor]

Found while editing the section. `R:\resolute-cleancheck` was written through a non-raw Python string, so `\r` became a carriage return and split the path across two lines in the committed TODO. The path appeared twice and was wrong both times.

**The near-misses are the point.** `\R` in `Bin\Release` and `\l` in `build\logs` both raised `SyntaxWarning` and survived intact. `\r` is a *valid* escape, so it produced no warning and silently destroyed the text. The warnings drew attention to the harmless cases and were silent on the damaging one.

Repaired, and the remaining edits to this section were written with raw strings.

## What the section actually achieved

The proof that matters is not that a build command exists but that the tree builds somewhere else:

```
R:\resolute-cleancheck, a different absolute path
  8,124 tracked files exported, no Bin/ and no build/
  toolchain supplied as a new machine would get it
  Release and Debug both build, both targets each
  tracked files changed by the build: 0
  launcher runs: window 'Resolute', responding
```

The last two lines are the falsifiable ones. "Builds without editing a single file" is measured by diffing the built tree against the index it came from, rather than asserted.

One unplanned check fell out of it: the two **Release** binaries are byte-identical to this tree's while the two **Debug** ones differ by a few hundred bytes. That is the expected signature of debug information embedding the build directory, which `§2` established when it found this build is not reproducible, and it is evidence that no build path reaches the shipped Release binary.

## Recorded rather than worked around

Exporting the tree into a deep path aborts with `Filename too long` on hundreds of files. The longest tracked path is 165 characters, inside `resolute_au3/samples/`, so the repository needs a root under roughly 95 characters or `core.longpaths` set on the clone. Nothing is wrong at `R:\conclave\projects\Resolute`, and "clone it anywhere and it builds" is not quite true. The failure is a checkout failure rather than a build failure, and the fix belongs on the clone rather than in this repository.
