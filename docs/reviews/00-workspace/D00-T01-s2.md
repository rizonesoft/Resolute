## The three questions

**Does it make sense?** Yes. The launcher ships as one file, 2,512,384 bytes, down from three files totalling 4,079,106.

**Is it logical?** After two rounds. The decisive correction is that "set once" now means one *file* every entry point includes, not one `CMakeLists.txt` that only one entry point reads.

**Did it break anything else?** It broke RegStudio's standalone build and I did not notice. That is F1 below, and it is the most instructive thing in this section.

## Findings

### F1 -- centralising the link flags broke the standalone extension build -- correctness -- FIXED in `820047c` (independent)

Raised by the independent review as a **P1**, the first of this project.

I removed `-static` from `extensions/RegStudio/CMakeLists.txt` because the root now set it, then wrote in the section that the change was "unbuilt" since RegStudio is commented out at `CMakeLists.txt:63`. Both halves were wrong in the same way: RegStudio is out of the *root* build, not out of the build. It is a standalone CMake project with its own `project()` call, and `reskit/Build-Extension.ps1` configures it with `cmake ..` from inside its own directory, so the root is never read on that path.

**The reviewer did not argue this. It built RegStudio standalone and found fresh `libc++.dll` and `libunwind.dll` imports** — an executable that would not start on a machine without them, which is what `AGENTS.md` forbids.

`cmake/ResoluteLinkPolicy.cmake` now holds the flags and both the root and the extension include it by path. Proven by building RegStudio the way its own script does: 17 imports, none a compiler runtime.

**The lesson is narrower than "test more".** I had a specific belief, that the code was not built, and I recorded it in the section as a reassurance instead of spending thirty seconds checking it. The reassurance is what made the defect invisible.

### F2 -- the build scripts had never worked -- correctness -- FIXED in `85c3707` (self)

Found by finally running them, which F1 should already have taught me to do and did not: I changed three scripts and verified the change by `grep`.

Three defects, and the first is not mine:

1. **PowerShell does not expand a variable in the bareword `-DNAME=$Var`.** The leading `-D` makes the whole token literal, so `CMAKE_BUILD_TYPE` was being set to the seven characters `$BuildType` and ninja choked on a rule named `CXX_SCAN__RegStudio_$BuildType`. **This form is in the original script.** These scripts have never configured a build type correctly. Quoting the argument fixes it.
2. The tool paths I added used Windows separators, and CMake writes them into its own cache files where a backslash is an escape, so `CMakeRCCompiler.cmake` failed to parse.
3. The script warned "No .exe found in build output" **immediately after linking one**, because it searched only the build directory while RegStudio sets `CMAKE_RUNTIME_OUTPUT_DIRECTORY` to its own `bin/`.

The third is the same failure as `§1`'s "reskit/ is unchanged": a script that misreports its own outcome teaches the reader to ignore it.

### F3 -- a reinterpret_cast defeated the type check it existed to enable -- correctness -- FIXED in `701fd87` (self)

Found by self-review. The direct binding used `reinterpret_cast<FnCreateBmp>(&LucideCreateHBitmap)`, and the signatures are identical, so the cast bought nothing and cost the check: it would have compiled whatever the signature later became. That is the opposite of what direct binding buys over `GetProcAddress`, which was the entire point of the change. It compiles as a plain assignment, which is the proof the signatures match.

### F4 -- "Bin/Release contains exactly one file" was true and readable as more -- record -- corrected (self)

Found by running the extension script, which deployed `RegStudio.exe` into `Bin/Release/System/`. The statement is about the **launcher**. `System/` is where extension executables deploy for discovery, which is the `RESEXT` model. What is gone is shared **libraries**, so no tool loads a DLL another tool owns. The section now says so.

### F5 -- a claim cited build output -- consistency -- corrected before shipping (self)

My own gitignored-path check, built in `D00 T04 §2`, refused a claim citing `Bin/Release/System`. It is build output, so the claim could not hold on any other clone. The single-file fact belongs in the driven evidence, and that is where it is.

Worth noting that the check caught its own author two sections after being written.

## What the section actually achieved

The thing keeping two DLLs alive was never the linker. `Resolute.exe` already imported neither: it links `ResoluteUI_static`, and Lucide was reached through `LoadLibraryW`, which **no import-table check can see**. That is why the section's checkpoint forbids proving this by imports, and why the proof is:

```
Bin/Release, launcher build          exactly one file
launched with no DLL anywhere        window 'Resolute', 4 control classes live
loaded Lucide/ResoluteUI modules     NONE
icon count from a linked binary      icons=29  first=badge-info
```

The last line is the one that distinguishes a working icon set from a missing one, because a launcher with no icons still draws a window.
