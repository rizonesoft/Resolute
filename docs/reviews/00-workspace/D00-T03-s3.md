## The three questions

**Does it make sense?** Yes. The section's argument is that the rename only gets more expensive as tools start including the headers, and `extensions/` carries no reference yet, so this is the cheapest moment. Nothing outside the rename was touched.

**Is it logical?** After F1, yes. The three export macros agree: `RESOLUTEUI_STATIC` is set `PUBLIC` on the static target, `RESOLUTEUI_BUILD` `PRIVATE` on the shared one, and `export.h` branches on both to define `RESUI_API`. A half-rename there would have broken the export macro silently, which is why the internal `EXOUI_BUILD` had to move with the public one.

**Did it break anything else?** The debug preset was built in this review and passes 52/52. The application was **run**, not merely compiled, because the riskiest part of this change cannot be caught by a compiler.

## Findings

### F1 -- three identifier families survived the rename -- consistency -- FIXED (self) [major]

The first pass renamed what the section's items enumerated and missed everything that carried the old prefix in another shape. The verification pattern shared the blind spot: `exo::|EXOUI|exo-ui|ExoUI|exo/|exokit|ExoKit` cannot match `WM_EXOTAB`, `ExoSidebar`, or `EXOEXT`, so the checkpoint reported clean over 25 surviving occurrences.

| Family | Count | Renamed to |
| --- | ---: | --- |
| `WM_EXOTAB`, the Tab-cycling message | 6 | `WM_RESUI_TAB` |
| Six window class names, `ExoSidebar` and siblings | 12 | `ResoluteSidebar` and siblings |
| `EXOEXT`, the extension discovery resource | 7 | `RESEXT` |

The section's Done-when is "no identifier or path carries the old name", which is broader than its enumerated list. That same reading is what justified renaming the CMake targets in the first pass, so applying it to these was consistency, not scope creep. Leaving them would have made the Done-when false while the row said `[x]`.

**`EXOEXT` was the one worth checking before touching.** It is not an internal name: `src/main.cpp` scans `System/*.exe` for an RCDATA resource of that name to discover extensions, so it is a contract between the launcher and every extension executable. Renaming a discovery contract with a producer still emitting the old name breaks scanning silently, with no build error and no crash, just an empty list.

Checked rather than assumed: `git grep EXOEXT -- extensions/` is empty, RegStudio's `resource.rc` does not emit it, and no extension executable is built into `System/` yet. The contract has **zero producers today**, so the rename is free now and will not be once tools start shipping. That is the same argument the section itself opens with.

The fixed pattern is now `[A-Za-z_]*exo[A-Za-z_]*`, case-insensitive, which matches any identifier containing the old prefix rather than the specific spellings someone thought to list.

### F2 -- the build is not reproducible -- reproducibility -- FILED to `D07 T01` (self) [major]

Found while satisfying item 4, which asked for a byte-comparison against the pre-rename build.

All three artifacts came back identical in size to the byte. The hashes differ, and the cause is not the rename. `Lucide.dll` is the control: its sources were never touched, `git status shared/lucide/` is empty, and its hash moved anyway. Two consecutive clean builds of identical sources then gave `8B25CFEE72714F28` and `08C187347BF55A19` at the same size.

So byte-comparison cannot attribute a hash difference to a source change here, and the section was asking for something this toolchain does not supply. Item 4 now records the finding and uses an instrument that works.

Filed rather than fixed because the mechanism is link options, and nothing in the tree asks for reproducibility yet. It has two real costs, both written into the filed item: a signed release cannot be independently tied to its tagged source, which matters for utilities that run elevated; and byte-comparison stays unavailable as a verification instrument.

## What replaced byte-comparison

```
llvm-nm --extern-only --defined-only Bin/Release/System/ResoluteUI.dll
  213  _ZN3rui     the new namespace
    0  _ZN3exo     the old one
  1429             total exported symbols
```

The third line is the falsifiability check. A count of zero for the old namespace proves nothing unless the same command demonstrably finds symbols, and it finds 1,429.

## The runtime check, and why it was owed

A window class name mismatch between `RegisterClassEx` and `CreateWindowEx` compiles cleanly and fails only when the window is created. Renaming six class names is exactly the change that produces one. Static check first, all six pairs matching, then the application was launched:

```
main window : handle present, title 'Resolute'
child classes: ResoluteListView  ResoluteSidebar  ResoluteStatusBar  ResoluteToolbar
```

Four of the six renamed classes instantiate in the default view. `ResoluteContentView` and `ResolutePopupMenu` are created on demand, so they do not appear here; both were verified pairwise in source.
