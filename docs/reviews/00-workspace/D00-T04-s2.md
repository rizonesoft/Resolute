## Findings

### F1-F2 -- raised by the independent review, both correct -- correctness -- FIXED in `e44995a` (independent)

**The wildcard bypass is the one worth reading twice.** `_ignored()` tested only the literal prefix before the first `*`, so `extensions/*/build/result.txt` was allowed while the identical literal path was rejected: the prefix `extensions/` is not ignored, and the file it resolves to is. The check built to stop machine-dependent claims was bypassable by writing the same claim with a glob, one commit after being built.

Fixing it made it worse before it worked, which is the part worth recording. The first attempt passed every resolved path to `git check-ignore -q`, and `-q` accepts **only one pathname**; more than one exits 128, which a returncode test reads as "not ignored". So the literal case started passing too. That was caught by re-running the probe rather than by trusting the fix, and the code now carries a comment saying why `-q` is absent, because the next person to touch it will reach for it.

The second, `--write` publishing a ledger it knew was incomplete, is the same shape as the defect `§1` fixed in the claims checker: a tool that carries on silently when it cannot read its input. Every mode now names the file, line, and reason, and `--write` refuses to publish.

### F3 -- the heading pattern matched ordinary headings -- correctness -- FIXED (self)

Found in this review by probing the regex rather than reading it. `^###\s+(F[\d\-, ]*\S.*)$` accepts any `###` heading beginning with F, so `### Findings`, `### Frozen check`, and `### Fixes applied` were all read as malformed findings.

It reported zero false positives today only because the existing findings files happen to use `## Findings` at the second level. The first reviewer to write `### Fixes applied` would have got a spurious error, and `--write` would have refused to publish over it.

**A check that fires on ordinary content gets switched off**, which is worse than not having the check: the four review findings above all survived because their checks were trusted. The pattern now requires `F<digits>` followed by a ` -- ` separator, which accepts `F1`, `F12`, `F1-F4`, and `F5 - F7`, and rejects every English word beginning with F.

### F4 -- the ledger goes stale on every review that does not regenerate it -- record -- FIXED in the skill (self)

Noticed while writing this file: the act of writing it makes `findings.md` stale, because the ledger is derived from files like this one. A ledger that is stale by construction after every review is a ledger nobody trusts by the third one.

`review-todo-section` now regenerates it at the stamp, with the reason stated and a note that a refusal to publish means a defect in the findings file just written. Fixing this in the skill rather than the tool is deliberate: the tool is correct, the workflow was incomplete.

## The repeat trigger, answered

The section requires that a category reaching two produces a recorded answer. Three are past two, and the answers are in the section rather than here. In summary:

| Category | Answer |
| --- | --- |
| `consistency` | one cheap check exists and was **built**: a claim may not cite a gitignored path. The rest of the category gets no single check, and the section says so |
| `record` | already has its check, which is `§1`. Some of them are a figure describing its own file, which no re-measurement can fix, so a rule replaces the check |
| `correctness` | every one is a check reporting success for its own absence. The answer is a discipline: a new check ships with a self-test that constructs its **failing** case |

No counts here either. Writing this file added findings and moved two of the three categories, which is the same trap the section records.

The `correctness` answer was tested immediately and by accident. Three of this section's own defects, F1 through F3, are that same inversion, and all three were found by constructing the failure rather than by reading the code.
