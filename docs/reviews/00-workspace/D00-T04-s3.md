## Findings

### F1-F3 -- raised by the independent review, all three correct -- correctness -- FIXED in `951e70a`

**F1 is the one to remember: the measurement was corrupted by its own documentation.** Commits were counted with `git log --grep=<ref>`, which matches the reference anywhere in a message. The commit introducing this report tabulated all six stamped sections in its body, so it counted as a commit of every one of them. Every row rose by one and the outlier vanished entirely:

```
before (mentions)            after (ownership)
D00 T03 §1  10 commits       D00 T03 §1  7 commits, rework yes
D00 T03 §2   3               D00 T03 §2  2, rework no
```

A measurement that its own documentation changes is not a measurement, and this one was wrong within minutes of being written. Ownership is now the repository's commit convention: a subject line ending in `(<ref>)`.

**F2**: git failing became an observation. `_commits_naming` returned 0 on exception and ignored `returncode` entirely, so a broken repository or a missing git produced a confident zero that entered the outlier arithmetic and would have entered the correlation as a section that cost nothing. It now raises and the report prints no rows: an unanswerable question is not an answer of zero.

**F3 is the one I should not have needed told.** The checklist required recording whether a section needed a follow-up commit after review. The implementation did not do it, and **I ticked the item anyway**. The item said it; the output did not have it. There is now a `rework` column, and it reads correctly on real data: `D00 T04 §1` and `§2` both show `yes`, which are `6cb2e1b` and `e44995a`, the two review-fix commits.

### F4 -- the whole git log was re-fetched once per section -- performance -- FIXED

Found in this review by measuring, which is how the equivalent finding in `§1` was found. `_owned_commits` ran `git log --format=%s --all` per stamped section: 380 subjects re-fetched six times today, a hundred and twenty times when the plan is finished, with the history growing underneath it.

Cached to one fetch. 0.4s to 0.3s at six sections, which understates it: the saving scales with sections and with history, and this is the second time in this TODO file that a new check quietly became the expensive part of its own tool.

### The mojibake, which is why F1 looked fine at first

Recorded because the first repr was convincing and wrong. After switching to ownership matching, every count read zero. Git emits UTF-8; Python decoded with the locale codec, cp1252 on Windows, so every marker came back as `Â§` and no subject matched.

A first check printed the output and it looked correct, because the terminal re-encoded it on the way to the screen. Only `repr()` of the raw slice showed `'(D00 T03 Â§4)'`. The lesson is narrow and worth keeping: **when a string comparison fails inexplicably, print `repr`, not the string.**

## What the section deliberately does not deliver

A correlation. Six stamped sections against a recorded threshold of thirty, and the tool prints the gap and says in full why it is not reporting one. `todo/README.md`'s sizing guidance is left unchanged with a dated note saying the data is insufficient.

That is the section's real content. The cheaper substitute, printing a coefficient over six points, is named in the checkpoint as the thing that fails it, because a figure that looks like evidence gets cited as evidence.
